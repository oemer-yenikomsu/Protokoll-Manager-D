Entwicklerdokumentation

Technische Übersicht zum Protokoll-Manager: Architektur, Module, API, Datenmodell, Geschäftsregeln und Betrieb. Für Entwickler und Master-Developer.

Python / Flask React / Tailwind SQLite / SQLAlchemy Stand: Mai 2026

Einführung

Der Protokoll-Manager ist eine interne Webanwendung zur Erfassung und Verwaltung von Gesprächsprotokollen. Diese Dokumentation richtet sich an Entwickler, die das System pflegen oder erweitern, und ist erst ab Rolle developer in der App sichtbar.

Schwerpunkt Geschäftsregeln (insbesondere die 72-Stunden-Bearbeitungsfrist) werden serverseitig durchgesetzt. Das Frontend spiegelt sie nur zur besseren Bedienung.

Architektur

Drei klar getrennte Schichten:

SchichtTechnologieAufgabe
Frontend (SPA)React, Vite, Tailwind CSSOberfläche, lokaler Zustand, API-Aufrufe
BackendPython, Flask, SQLAlchemy, WaitressREST-API, Geschäftsregeln, Authentifizierung
DatenhaltungSQLite (Datei protokoll.db)Persistenz, idempotente Schema-Migration

Im Entwicklungsmodus laufen Vite (Port 5173) und Flask (Port 5000) parallel, das Vite-Proxy leitet /api/* an Flask weiter. Im Produktivmodus liefert ein einzelner Flask/Waitress-Prozess sowohl die API als auch das gebaute Frontend aus frontend/dist aus.

Backend / API

Die REST-API liegt unter dem Präfix /api/. Ein before_request-Hook prüft die Anmeldung für alle API-Aufrufe außer Login und Konfiguration.

backend/app.py 
@app.before_request
def require_login_for_api():
    if request.method == 'OPTIONS':
        return None
    if not request.path.startswith('/api/'):
        return None
    if request.path.startswith('/api/auth/login') or request.path == '/api/auth/config':
        return None
    get_current_benutzer_or_401()
    return None

Wichtige Endpunkte

MethodeRouteZweck

POST/api/auth/logoutSitzung beenden

Bei HTTP 403 liegt entweder eine Berechtigungsverletzung oder ein Verstoß gegen die 72-Stunden-Regel vor; die Detailmeldung steht in description.

Kerntabelle protokoll mit Audit-Feldern

backend/models.py 
class Protokoll(db.Model):
    __tablename__ = 'protokoll'
    protokoll_id      = db.Column(db.Integer, primary_key=True)
    datum             = db.Column(db.Date, nullable=False)
    ort               = db.Column(db.String(300), default='')
    typ               = db.Column(db.String(100), nullable=False)
    autor_id          = db.Column(db.Integer, db.ForeignKey('benutzer.benutzer_id'), nullable=False)
    erstellt_am       = db.Column(db.DateTime, nullable=False, default=datetime.utcnow)
    bearbeitet_von_id = db.Column(db.Integer, db.ForeignKey('benutzer.benutzer_id'), nullable=True)
    bearbeitet_am     = db.Column(db.DateTime, nullable=True)
    eintraege         = db.relationship(
        'Eintrag', back_populates='protokoll',
        cascade='all, delete-orphan'
    )

Aufgaben sind als JSON-Array am Eintrag gespeichert ({text, status}); lookup nutzt einen Unique-Constraint auf (kategorie, wert) zur Dublettenvermeidung.

Authentifizierung & Rollen

Anmeldung über Benutzername und Passwort. Passwörter werden mit werkzeug.security als Hash gespeichert; das Sitzungs-Cookie ist HTTP-Only. Eine Idle-Prüfung beendet inaktive Sitzungen automatisch.

72-Stunden-Regel

Schreibroutinen für Protokoll und Eintrag prüfen vor jeder Änderung die Frist mit der zentralen Hilfsfunktion is_editable.

backend/app.py 
def is_editable(erstellt_am: datetime) -> bool:
    return (datetime.utcnow() - erstellt_am) <= timedelta(hours=72)


@app.route('/api/protokolle/<int:protokoll_id>', methods=['PUT'])
def update_protokoll(protokoll_id):
    protokoll = Protokoll.query.get_or_404(protokoll_id)
    if not is_editable(protokoll.erstellt_am):
        abort(403, description='Bearbeitung nach 72h gesperrt.')
    ...
AktionNach 72 h
Protokoll / Eintrag bearbeiten oder löschenGesperrt (403)
Aufgabenstatus ändernWeiter möglich (eigene Route)
Kommentar hinzufügenWeiter möglich
Organisation einer Person ändernNur 72 h nach Personen-Anlage

Das Frontend spiegelt die Regel über checkIsEditable in App.jsx — die endgültige Durchsetzung erfolgt im Backend.

Deployment

Die Anwendung läuft im Produktivbetrieb auf einem Windows-Host-PC im Firmennetz. backend/run_production.py bündelt API und gebautes Frontend in einem Prozess (Waitress).

backend/run_production.py (Auszug) 
if __name__ == '__main__':
    ensure_benutzer_schema(app)
    port = int(os.getenv('PORT', '5000'))
    host = os.getenv('HOST', '0.0.0.0')

    if not _frontend_ready():
        print('FEHLER: frontend/dist fehlt.')
        raise SystemExit(1)

    ip = _lan_ip()
    print(f'  Lokal:    http://127.0.0.1:{port}')
    print(f'  Im Firmennetz: http://{ip}:{port}')
    serve(app, host=host, port=port, threads=4)

Inbetriebnahme

  1. INSTALL.bat — installiert bei Bedarf Python/Node per winget, richtet venv ein, baut frontend/dist.
  2. START.bat — startet Waitress + statisches Frontend (oder python backend/run_production.py).
  3. Erreichbarkeit prüfen: Browser auf http://<Host-IP>:5000.
  4. Initiale Benutzer-Passwörter über die Benutzerverwaltung anpassen lassen.

Backup & Migration

Die Datenbank ist eine einzelne SQLite-Datei. Sicherung über das Menü (Datei-Download) oder durch Kopieren der Datei backend/protokoll.db. Import über das Menü überschreibt die aktuelle DB — vorher wird automatisch eine Kopie heruntergeladen.

Schema-Migration

Beim Start ruft app.py ensure_benutzer_schema(app) aus schema_migrate.py. Die Funktion prüft den Ist-Zustand und ergänzt fehlende Tabellen oder Spalten, ohne Daten zu verlieren. Erweiterungen am Datenmodell sollten dort als idempotente Schritte ergänzt werden.

Vor jeder Schema-Änderung protokoll.db sichern. SQLite kennt kein vollständiges ALTER TABLE; manche Änderungen erfordern CREATE TABLE … new + INSERT … SELECT + DROP + RENAME (Beispiele siehe _rebuild_protokoll_for_benutzer_fk).

FAQ Entwickler

Wo wird die 72-Stunden-Regel durchgesetzt?

Server in backend/app.py über is_editable(erstellt_am); Client spiegelt nur die Anzeige (Schloss-Symbol). Neue Schreib­routinen müssen die Prüfung explizit aufrufen.

Wie ergänze ich einen neuen Endpoint?

Route in app.py definieren, im Frontend api.js einen passenden Helfer ergänzen und in der jeweiligen View aufrufen. Bei Schreibrouten Authentifizierung (greift automatisch) und Audit-Felder beachten.

Wie fügt man eine neue Rolle hinzu?

backend/roles.py: Rollenkonstante, VALID_ROLLEN, ROLLE_STUFE, ROLLE_LABEL. Anschließend im Frontend in utils/roles.js dieselben Konstanten ergänzen.

Wie wird das Frontend produktiv ausgeliefert?

Über npm run build entsteht frontend/dist. run_production.py liefert daraus statische Assets und reicht /api/* an Flask weiter. Im Entwicklungsmodus läuft Vite separat mit Proxy auf localhost:5000.

Warum sehe ich diese Seite, andere Benutzer aber nicht?

Der Menüeintrag ist erst ab Rolle developer sichtbar (darfEntwicklerdoku in utils/roles.js). Die statische HTML-Seite selbst ist unter ihrer URL aufrufbar — eine zusätzliche Server-Prüfung ist nicht implementiert, weil die Inhalte keine geheimen Schlüssel enthalten.
